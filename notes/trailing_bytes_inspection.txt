External IDL/docs research:
- Official Meteora DLMM docs say PositionV2 supports up to 1,400 bins per position, increased from the previous 70-bin limit.
- The same docs say this is achieved through extended byte data attached to the position account and allocated on demand as the position grows.
- Official Meteora dlmm.json IDL contains PositionBinData with bytemuck C layout:
  liquidity_share u128 (16B) + reward_info UserRewardInfo (48B) + fee_info FeeInfo (48B) = 112B.

Interpretation:
- For a 9464B PositionV2 account, raw_len - 8120 = 1344B.
- 1344B = 12 * 112B and also 42 * 32B, but the official Dynamic Positions docs make 12 extra PositionBinData slots the structurally expected interpretation.
- That means the bytes after 8120 are most likely PositionV2 dynamic extension bin records, not LimitOrder headers and not LimitOrderBinData.
- These bytes can have NAV value when their liquidity_share is non-zero, because they extend the position's bin range/liquidity accounting.
- The current script now tests all three interpretations once RPC access is available:
  LimitOrder header, LimitOrderBinData, and PositionBinData extension.

Expected decisive live-RPC signal:
- If bytes[8120:8152] as a pubkey does not match the account lb_pair at offset 8, LimitOrder header is rejected.
- If bytes[8120:8128] as amount plus bin_id/is_ask at 8136/8140 are nonsensical, LimitOrderBinData is rejected.
- If the 1344 trailing bytes split into 12 x 112B records with plausible PositionBinData fields, the trailing bytes are PositionV2 dynamic bin data.
